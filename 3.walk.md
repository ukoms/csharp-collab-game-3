### Kontrakt klasy DziennikWyprawy

- Osobny plik `DziennikWyprawy.cs` w tym samym projekcie co Program.cs, na tym etapie bez własnej przestrzeni nazw (`namespace`). Plik klasy nie zawiera instrukcji najwyższego poziomu ani drugiego Main.
- Pola przechowujące tablice są prywatne i należą do instancji, bez static. Program nie otrzymuje tablic do samodzielnej zmiany.
- Obiekt odpowiada za odkrycia i trzy ostatnie wpisy wyprawy. Energia, ruch, przedmioty i koniec gry pozostają jeszcze w Program.cs - ich przeniesienie to C4.

| Składowa publiczna | Umowa |
|---|---|
| `DziennikWyprawy()` | Konstruktor bez parametrów ustanawia stan taki jak Reset. |
| `int LiczbaOdwiedzonych { get; }` | Tylko odczyt; wynik obliczany z prywatnych flag przez pętlę. Nie jest drugim, niezależnie aktualizowanym licznikiem. |
| `int LiczbaWpisow { get; private set; }` | Liczba zajętych pozycji dziennika 0–3; klient nie może jej przypisać. |
| `void Odwiedz(int numer)` | Dla 1–4 oznacza pokój; ponowna wizyta niczego nie zwiększa. Dla numeru spoza zakresu nic nie zmienia. |
| `bool CzyOdwiedzono(int numer)` | Odczyt flagi; dla numeru spoza 1–4 zwraca false. |
| `void DodajWpis(string? tresc)` | Ignoruje null, pusty tekst i same spacje. Poprawny tekst zapisuje po Trim. Przy pełnych 3 wpisach usuwa najstarszy, zachowując kolejność. |
| `string PobierzWpis(int indeks)` | Zajęte wpisy mają indeksy 0..LiczbaWpisow-1, od najstarszego. Dla innych indeksów zwraca pusty napis; nie rzuca wyjątku w tym ćwiczeniu. |
| `void Reset()` | Cztery flagi odkryć: tylko pokój 1 odwiedzony; dziennik pusty, LiczbaWpisow=0. Czyści także stare teksty w tablicy. Nie tworzy drugiego obiektu. |

- W tabeli opisano API, nie gotowy kod do wklejenia. Getter LiczbaOdwiedzonych wymaga własnego ciała obliczającego wynik.
- Prywatna tablica wpisów ma stałą długość 3. Zainicjalizuj wszystkie elementy pustymi napisami; nie polegaj na niejawnych null w nowej tablicy stringów.
- W minimum nie wprowadzamy własnej obsługi wyjątków, dziedziczenia, `List`, LINQ, zapisu do plików ani pakietów testowych. Ich użycie nie jest potrzebne do wykonania tego collaba.

### Reguły wpisów

- Dokładnie jeden wpis po każdym udanym `lewo`, `prawo`, `karta`, `bezpiecznik`, `napraw` i `wyjdz`.
- Wpis ruchu wskazuje miejsce docelowe; wpis akcji opisuje jej skutek. Treść może pasować do fabuły, ale znaczenie musi być jednoznaczne.
- Wpis dodaj po zaakceptowaniu zmiany i przed dotychczasowym ZakonczTure, również dla ostatniej czynności kończącej rozgrywkę.
- Nie zapisuj `start`, informacji, nieznanych komend, pustego wejścia, odmów ani samych komunikatów o końcu gry. Start czyści historię, nie dopisuje własnego wpisu.
- Oznaczenie odwiedzin samo nie dopisuje zdarzenia - powrót do znanego pokoju nadal jest udanym ruchem i wymaga wpisu od obsługi ruchu.
- Klasa nie używa Console, nie nalicza energii i nie rozstrzyga zwycięstwa. Program wyświetla odczytane dane.

### Git - obowiązkowy przebieg

- Przed pracą ustalcie nazwę głównej gałęzi w GitHubie i README. Przykład używa `master`, zgodnie z repozytorium bazowym; przy `main` zamieńcie nazwę we wszystkich poleceniach. Nie twórzcie przypadkowo drugiej głównej gałęzi.
- Pracujcie w katalogu z `.csproj`; jeśli gra działa, zakończcie ją przed poleceniami terminala.

```bash
git status
git switch master
git pull --ff-only
dotnet build
git switch -c feature/collab-zadanie
```

- `feature/collab-zadanie` zastąp własną nazwą, np. `feature/c03-odkrycia` albo `feature/c03-dziennik`. Każda osoba używa innej gałęzi. Zacznij od czystego katalogu; własne zmiany zapisz przed przełączeniem.
- Po małej zmianie: `git diff`, `dotnet build`, `dotnet run`, właściwe próby, zamknięcie gry.
- Dodaj jawnie zmienione pliki przez `git add NAZWA_PLIKU` (to miejsce na prawdziwą nazwę), obejrzyj `git diff --staged`, zrób commit opisujący zmianę i `git push -u origin NAZWA_GALEZI`.
- Otwórz PR do faktycznej głównej gałęzi; kolega sprawdza warunki, reset i koszt. Integrator scala przez GitHub po jednej gałęzi; nie wykonuje drugiego merge tej samej zmiany lokalnie.
- Po każdym scaleniu pobierz główną gałąź do czystej kopii i wykonaj build oraz właściwe próby. Własną niezakończoną gałąź aktualizuj przez `git fetch origin`, potem `git merge origin/master` po zapisaniu swojej pracy w commicie.
- Jeśli wystąpi konflikt, przeczytaj obie wersje z autorem i sprawdź wynik. Bez force-push i resetowania w ciemno. `pull --ff-only` może odmówić przy rozbieżności - wtedy sprawdź historię.
- Końcowy tag tworzy tylko integrator na odebranej głównej gałęzi; nazwa tagu jest podana w briefie. Nie nadpisuj istniejącego tagu: użyj kolejnej wersji.
- Po odbiorze integrator wykonuje `git tag collab-03-core-v1` i `git push origin collab-03-core-v1`. Jeśli ten tag już istnieje, uzgodnij kolejną nazwę, np. `collab-03-core-v2`, i użyj jej w obu poleceniach oraz przekazaniu.

3. Tworzy plan zmiany: stara tablica odkryć -> metody obiektu; stary licznik -> getter. Wskazuje dodatki odczytujące stare dane.
4. W parze obowiązki te rozdzielają A i B; wspólne fragmenty robią na zmianę przy klawiaturze.
5. Nikt nie powinien czekać na gotowy pełny dziennik, aby prześledzić i przetestować sposób wyświetlania.

#### Zatrzymaj się po kroku 7

- Zapisz listę miejsc integracji: Start, ruch, mapa, odkrycia, każda udana akcja oraz komenda dziennik.

### Krok 8. Przełącz grę dopiero po próbach klasy

#### Zatrzymaj się po kroku 8

- Wyszukaj nazwę dawnej tablicy odwiedzin w całym projekcie. Jeśli pozostał zapis lub odczyt, ustal, czy migracja jest kompletna.
- Wyszukaj wywołania dodawania wpisów. Każde powinno odpowiadać jednej zaakceptowanej czynności, nigdy samemu odczytaniu komendy.
- Uruchom mapę i dziennik kilka razy bez ruchu. Porównaj energię, liczbę odkryć i liczbę wpisów przed odczytami i po nich.
- Nie uznawaj przełączenia za ukończone, jeśli tylko ruch korzysta z nowego obiektu. Mapa, reset i odkrycia muszą korzystać z tego samego źródła.

### Krok 9. Odbierz zachowanie

1. Każda osoba wykonuje część T3.1–T3.12; druga sprawdza jej wyniki.
2. Dwie instancje muszą być niezależne. Samo `b = a` nie jest próbą dwóch instancji.
3. Sprawdź ostatni wpis po wygranej i po przegranej. Nie dopisuj jeszcze dodatkowego komunikatu końca jako osobnego zdarzenia.
